# SSH Detection Logic

## 1. Detection Objective

The objective of this detection is to identify repeated SSH authentication failures that may indicate brute-force, password-spraying, credential misuse, or other suspicious authentication activity.

The current project performs this detection manually using native Linux telemetry. It does **not** claim that a SIEM or automated alerting platform is deployed.

---

## 2. Primary Log Source

The primary telemetry source is the Ubuntu SSH service journal.

```bash
sudo journalctl -u ssh --no-pager
```

The authentication log can also be reviewed:

```bash
sudo grep -a "sshd" /var/log/auth.log
```

---

## 3. Relevant Event Pattern

A typical failed OpenSSH authentication event contains a pattern similar to:

```text
Failed password for <username> from <source-ip> port <source-port> ssh2
```

Important fields include:

| Field | Example |
|---|---|
| Timestamp | `2026-09-09 07:58:55` |
| Username | `lexa` |
| Source IP | `192.168.56.20` |
| Source Port | `44560` |
| Service | `sshd` |
| Destination Port | `22` |
| Result | `Failed` |

---

## 4. Basic Detection

To identify failed SSH authentication:

```bash
sudo journalctl -u ssh --no-pager | grep "Failed password"
```

This produces the candidate events that require analyst review.

### Important

A single failed login should generally be treated as an **authentication-failure event**, not automatically as a confirmed attack.

The analyst needs context before escalation.

---

## 5. Event Counting

The lab contained three actual failed SSH authentication events.

The service-specific journal was used to avoid counting unrelated entries or the analyst's own log-search commands.

```bash
sudo journalctl -u ssh --no-pager | grep "Failed password"
```

### Why service-specific filtering matters

Broad searches of `/var/log/auth.log` can include records generated by the investigation commands themselves.

Therefore:

```text
Raw grep result
      ↓
Validate event source
      ↓
Filter for sshd authentication events
      ↓
Manually review
      ↓
Count actual security events
```

## 6. Detection Fields

A useful SSH detection should extract:

```text
timestamp
source_ip
destination_host
username
source_port
destination_port
authentication_result
authentication_method
```

For the lab:

```text
source_ip:            192.168.56.20
destination_host:     ubuntu-server
destination_ip:       192.168.56.10
username:             lexa
destination_port:     22
result:               Failed
```

---

## 7. Correlation Logic

A basic repeated-failure detection can be represented as:

```text
IF
    authentication_service = SSH
AND
    authentication_result = Failed
AND
    multiple events share the same source IP
WITHIN
    a defined time window
THEN
    generate a suspicious SSH authentication alert
```

Example laboratory threshold:

```text
3 or more failed SSH authentications
from the same source IP
within 15 minutes
```

This is an example threshold for demonstration. Production thresholds should be tuned using the organization's normal authentication patterns.

---

## 8. Source IP Correlation

The source IP is extracted from the SSH event:

```text
Failed password for lexa from 192.168.56.20 ...
```

The network path can be independently validated:

```bash
ip route get 192.168.56.10
```

Lab result:

```text
192.168.56.10 dev eth1 src 192.168.56.20
```

This correlates:

```text
SSH log source
      +
Network configuration
      =
Higher-confidence source identification
```

---

## 9. Successful Login Correlation

Repeated failures should be correlated with successful authentication.

Search successful events:

```bash
sudo journalctl -u ssh --no-pager | grep "Accepted password"
```

Search both outcomes together:

```bash
sudo journalctl -u ssh --no-pager | grep -E "Accepted password|Failed password"
```

### Investigation Question

Did a successful authentication occur after repeated failures?

If yes, the analyst should investigate:

- account ownership
- source IP
- login time
- session activity
- commands executed
- privilege escalation
- persistence
- file changes
- network activity

## 10. Alert Enrichment

A useful alert should contain more than:

```text

```

Recommended fields:

```text

```

Example:

```text

Service:                SSH

Severity:               Low

```

## 11. False-Positive Handling

A detection alert does not automatically mean malicious activity.

Before escalation, determine:

1. Is the source IP known?
2. Does it belong to an administrator or test system?
3. Was the activity authorized?
4. Is the account expected?
5. Were there repeated attempts?
6. Was there a successful login?
7. What happened after authentication?

### Lab Example

```text
192.168.56.20
       ↓
Known Kali workstation
       ↓
Authorized security testing
       ↓
Three failed SSH events
       ↓
No confirmed compromise
       ↓
Controlled Security Testing
```

---

## 12. Severity Concept

Severity should be based on evidence and context.

### Example: Lower-priority authentication event

```text
Single failed login
Known internal source
No successful authentication
No suspicious follow-up activity
```

### Example: Higher-priority investigation

```text
Repeated failures
Unknown source
Multiple targeted accounts
Followed by successful authentication
Suspicious post-login activity
```

This is a conceptual framework rather than a universal production severity standard.

---

## 13. Detection vs Investigation

The project separates detection from incident classification.

```text
Detection
    ↓
"Multiple SSH authentication failures observed"
    ↓
Investigation
    ↓
"Source is 192.168.56.20"
    ↓
Correlation
    ↓
"Source is authorized Kali testing workstation"
    ↓
Classification
    ↓
"Controlled Security Testing"
```

This is an important SOC principle:

> **An alert is not automatically a confirmed incident.**

## 14. MITRE ATT&CK Mapping

The observed repeated authentication-failure behavior is mapped to:

**T1110 — Brute Force**

The mapping describes the observed behavior pattern.

It does **not** establish that an actual external adversary performed the activity.

In this lab, the behavior was intentionally generated for authorized testing.

## 15. Detection Pseudocode

```text
FOR each SSH authentication event:

    IF result == "Failed":

        extract source_ip
        extract username
        extract timestamp

        add event to source_ip counter

        IF failures from source_ip >= threshold
           within time_window:

            create alert

            enrich alert with:
                destination
                username
                first_seen
                last_seen
                asset_context

            check for successful authentication

            IF successful_login_after_failures:
                increase investigation priority

            send to analyst for investigation
```

## 16. Manual SOC Implementation

The current project demonstrates the underlying logic manually.

### Detect failures

```bash
sudo journalctl -u ssh --no-pager | grep "Failed password"
```

### Detect successful authentication

```bash
sudo journalctl -u ssh --no-pager | grep "Accepted password"
```

### Correlate both

```bash
sudo journalctl -u ssh --no-pager | grep -E "Accepted password|Failed password"
```

### Verify SSH service

```bash
sudo systemctl status ssh --no-pager
```

### Verify port 22

```bash
sudo ss -lntp | grep ':22'
```

## 19. Password Spraying vs Brute Force

The analyst should distinguish authentication patterns.

### Brute Force

Typically:

```text
One account
+
Many password attempts
```

### Password Spraying

Typically:

```text
One/common password
+
Many different accounts
```

The raw SSH logs can provide usernames and source IPs needed to investigate these patterns.

---

## 20. Detection Limitations

This detection has limitations:

- Native logs may not provide complete network context.
- NAT or proxies can obscure the original source in some environments.
- Thresholds can generate false positives.
- Distributed attacks can use many source IPs.
- Slow attacks may remain below a simple frequency threshold.
- A failed login alone does not establish malicious intent.
- Additional endpoint and identity telemetry may be required.

Therefore, detection logic should be combined with contextual investigation.

## 21. Analyst Investigation Workflow

```text
1. Receive authentication alert
        ↓
2. Validate log event
        ↓
3. Extract source IP
        ↓
4. Identify target account
        ↓
5. Count failures
        ↓
6. Establish time window
        ↓
7. Check successful authentication
        ↓
8. Validate source asset
        ↓
9. Review post-login activity
        ↓
10. Determine false positive / suspicious activity
        ↓
11. Map behavior if appropriate
        ↓
12. Document findings
        ↓
13. Escalate or close
```

## 22. Interview Explanation

A concise interview answer:

> "I designed a detection for repeated SSH authentication failures. I first filter OpenSSH logs for failed authentication events, extract the source IP, username and timestamp, then correlate multiple failures from the same source within a defined time window. I also check whether a successful login occurred after the failures and investigate post-authentication activity. In my lab, three actual failed events originated from the authorized Kali workstation, so the alert was classified as controlled security testing rather than a confirmed compromise."
