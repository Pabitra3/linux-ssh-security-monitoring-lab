# False Positive Analysis — SSH Authentication Activity

## 1. Purpose

This document explains how the SOC analyst determines whether observed SSH authentication failures represent a genuine security incident, benign user activity, or authorized security testing.

The analysis uses the evidence collected from the Linux SSH Security Monitoring & Incident Investigation Lab.

---

## 2. Detection Trigger

The investigation was triggered by repeated failed SSH authentication events on the Ubuntu Server.

Observed values:

```text
Source IP:       192.168.56.20
Destination IP:  192.168.56.10
Service:         SSH
Destination Port: 22
Target Account: lexa
Failed Events:   3
```

The relevant event pattern was:

```text
Failed password for lexa from 192.168.56.20
```

A failed authentication event is an investigation indicator. It is not, by itself, proof of compromise.

---

## 3. Initial Analyst Questions

When a failed SSH authentication alert is observed, the analyst should ask:

1. Which source IP generated the event?
2. Which destination host was targeted?
3. Which account was targeted?
4. How many failures occurred?
5. How quickly did the failures occur?
6. Was authentication eventually successful?
7. Is the source IP known or expected?
8. Was the activity authorized?
9. What happened after any successful login?
10. Is there evidence of persistence, privilege abuse, or other suspicious activity?

---

## 4. Source IP Validation

The failed SSH events identified:

```text
192.168.56.20
```

as the source address.

The lab network was:

```text
192.168.56.0/24
```

The known systems were:

```text
Kali-Attacker   192.168.56.20
Ubuntu-Server   192.168.56.10
```

The Kali route to the Ubuntu Server was validated using:

```bash
ip route get 192.168.56.10
```

The route showed:

```text
192.168.56.10 dev eth1 src 192.168.56.20
```

This correlates the source IP in the SSH logs with the Kali testing workstation.

---

## 5. Authentication Event Analysis

Three actual failed SSH authentication events were identified.

The events occurred at:

```text
2026-09-09 07:58:55
2026-09-09 13:09:40
2026-09-09 13:11:02
```

The events targeted:

```text
Account: lexa
Service: SSH
Port: 22
Source: 192.168.56.20
```

The repeated failures are consistent with the detection pattern being investigated.

However, the number of failed events alone does not establish malicious intent.

---

## 6. Authorization Check

The source workstation was the Kali machine used by the analyst for controlled security testing.

The SSH authentication failures were intentionally generated as part of the SOC lab exercise.

Therefore:

```text
Source IP
     ↓
192.168.56.20
     ↓
Known Kali lab workstation
     ↓
Authorized test activity
```

This is a critical contextual finding.

In a production environment, the analyst would need to validate the source through asset inventory, user confirmation, change records, ticketing systems, endpoint telemetry, or other authorized sources.

---

## 7. Successful Authentication Check

A failed authentication event becomes more significant when it is followed by a successful authentication that cannot be explained by the user or expected activity.

The investigation therefore correlated:

```bash
sudo journalctl -u ssh --no-pager | grep -E "Accepted password|Failed password"
```

The available evidence showed successful SSH authentication events and the controlled failed authentication events.

There was no evidence in the collected lab data of a successful unauthorized login immediately following the controlled failed attempts.

---

## 8. Post-Authentication Activity

The investigation also reviewed privileged activity.

The command:

```bash
sudo whoami
```

returned:

```text
root
```

The corresponding sudo log contained:

```text
COMMAND=/usr/bin/whoami
USER=root
```

This activity was generated by the analyst during investigation.

It should therefore not be incorrectly classified as malicious privilege escalation.

This demonstrates an important SOC principle:

> A suspicious-looking event must be correlated with context before assigning an incident classification.

---

## 9. False Positive Decision Process

The decision process used in this lab can be represented as:

```text
Failed SSH Authentication
          |
          v

          |
          v

     /             Yes           No
    |             |
    v             v

    |
    v

     /             Yes           No

    v             v
```

## 10. Lab Classification

Based on the collected evidence:

| Investigation Factor | Finding |
|---|---|
| Failed SSH attempts | 3 actual events |
| Source IP | `192.168.56.20` |
| Source system | Kali-Attacker |
| Target IP | `192.168.56.10` |
| Target system | Ubuntu-Server |
| Target account | `lexa` |
| Service | SSH |
| Port | 22 |
| Activity authorization | Authorized lab testing |
| Confirmed compromise | No |
| Malicious persistence observed | No |
| Classification | Controlled security testing |

The events are therefore treated as **benign authorized security-testing activity within this lab**.

---

## 11. Important SOC Distinction

The lab demonstrates the difference between:

### Alert

A technical condition was detected.

Example:

```text
Multiple failed SSH authentication attempts
```

### Investigation

The analyst gathers context and supporting evidence.

Example:

```text
Source = known Kali workstation
Target = lab Ubuntu Server
Activity = authorized test
```

### Classification

The analyst determines how the event should be handled.

For this lab:

```text
Controlled Security Testing
```

An alert should not automatically be treated as a confirmed compromise.

---

## 12. What Would Make This More Suspicious?

In a real production environment, the following additional evidence could increase the need for investigation:

- Unknown external source IP
- Large number of failures in a short period
- Attempts against many usernames
- Attempts against multiple hosts
- Successful authentication after repeated failures
- Successful login from an unusual source
- New or unexpected privileged activity
- Creation of new accounts
- Changes to SSH configuration
- Persistence mechanisms
- Unexpected processes or services
- Suspicious outbound network connections
- File modifications following authentication

These indicators should be correlated rather than evaluated independently.

## 15. Limitations

This lab has important limitations:

- The source IP is an internal lab address.
- The environment contains only a small number of systems.
- No enterprise identity provider is present.
- No centralized SIEM is deployed.
- No external threat-intelligence enrichment was required.
- The activity was intentionally generated and therefore has known authorization context.
- The investigation cannot be used to claim that the same pattern would always be benign in production.

In a real SOC, classification would require additional telemetry and organizational context.

---

## 16. Interview Explanation

A concise interview answer:

> "I don't classify every failed SSH login as an attack. I first identify the source and destination, correlate the source IP with the asset, check the targeted account and failure count, and then look for successful authentication and post-authentication activity. In my lab, three failed SSH events came from the known Kali testing workstation at 192.168.56.20 targeting the Ubuntu Server at 192.168.56.10. Because the activity was intentionally generated as authorized security testing and I found no evidence of unauthorized compromise, I classified it as controlled security testing rather than a confirmed compromise."

---

## 17. Conclusion

The investigation demonstrates that effective SOC analysis requires **context and correlation**, not simply matching a suspicious log string.

The core principle demonstrated by this project is:

```text
Detection ≠ Incident
Incident Indicator ≠ Confirmed Compromise
```

The analyst must validate the event using source identity, target context, authentication history, authorization status, and post-authentication activity before assigning a final classification.
